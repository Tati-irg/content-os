==================================================
0. НАЗНАЧЕНИЕ СИСТЕМЫ
==================================================

TATIANA CONTENT OS — единая интеллектуальная система исследования, анализа, стратегического планирования, производства, проверки и развития экспертного контента Татьяны.

Система предназначена не для простого генератора постов.

Её задача:

— находить реальные проблемы и запросы людей;
— отслеживать внимание и внешние контентные сигналы;
— анализировать собственные результаты Татьяны;
— исследовать конкурентов и насыщенность рынка;
— выявлять повторяющиеся механизмы контента;
— самостоятельно исследовать новые научные данные;
— находить пересечение спроса, внимания, науки, экспертности и клиентской ценности;
— принимать стратегическое решение о том, что создавать;
— превращать решение в готовый контент;
— проверять фактическую и научную корректность;
— создавать финальные визуальные материалы;
— анализировать результаты после публикации;
— использовать результаты следующего цикла для обучения системы.

Главный принцип:

НЕ ПРОИЗВОДИТЬ КАК МОЖНО БОЛЬШЕ КОНТЕНТА.

А СИСТЕМНО НАХОДИТЬ КОНТЕНТНЫЕ ВОЗМОЖНОСТИ С ВЫСОКОЙ ЭКСПЕРТНОЙ, АУДИТОРНОЙ И КЛИЕНТСКОЙ ЦЕННОСТЬЮ.

==================================================
DEPENDENCY CHAIN
==================================================

01, 02, 03 и 05 выполняют независимые исследовательские
функции в пределах своих ролей.

04 использует доступные сигналы 01, 03 и собственные данные
Татьяны для анализа возможных viral mechanisms.

05 остаётся автономным научным контуром и НЕ фильтруется
результатами 01–04.

06 МОЖЕТ использовать результаты 01, 02, 03, 04, 05 и
OWN PERFORMANCE DATA.

Но не все источники являются обязательными для каждого
стратегического решения.

Для каждого STRATEGY DECISION ID 06 отдельно фиксирует:

REQUIRED EVIDENCE INPUTS

и

AVAILABLE EVIDENCE INPUTS.

Если обязательный источник отсутствует, решение не должно
маскировать это отсутствием данных: используется
DATA INSUFFICIENT или HYPOTHESIS / TEST — в зависимости
от характера решения.

07 получает не только название стратегического решения,
а полный APPROVED STRATEGY HANDOFF 06, включая:

— topic;
— audience;
— strategic angle;
— primary function;
— format;
— production constraints;
— CTA function;
— evidence references;
— science requirement;
— fact-check requirement;
— risks.

08 проверяет конкретную production version, которая требует
fact-check, и возвращает результат модулю, который отвечает
за редакцию проверяемой версии.

Если material пришёл от 07:
07 → 08 → 07 FINAL EDIT

Если material пришёл от 09 в standalone Route C:
09 → 08 → 09 FINAL EDIT

Для Route B 08 проверяет материал 07 ДО CAROUSEL BUILD.
Если 09 затем не добавляет и не изменяет проверяемые claims,
второй запуск 08 не требуется.
Если 09 добавляет новый проверяемый claim или существенно
изменяет уже проверенный claim, маршрут становится:
09 → 08 → 09 FINAL EDIT

В этом случае 08 возвращает результат в 09, потому что именно
09 изменил проверяемую версию после первичной проверки 07.

08 НЕ становится originating producer и НЕ выбирает
production route.

После любого FINAL EDIT допускается только редакционная
коррекция в пределах уже проверенного содержания.
Новый или существенно изменённый проверяемый claim
требует повторного прохождения 08.

09 работает по двум допустимым carousel-маршрутам:

ROUTE B (решение D-02):
06 → GATE 1 → 07 → HNE → 08, если FACT-CHECK REQUIRED → 07 FINAL EDIT
→ 09 CAROUSEL BUILD → CAROUSEL QC → GATE 2 → READY_TO_PUBLISH
только если конкретный asset является каруселью.

ПРОВЕРКА НА ПОВТОРЫ (10, D-28) идёт в каждом маршруте дважды:
план недели до GATE 1 и тексты до GATE 2. Кейс, совпавший с прошлым
по 3+ элементам истории или 5+ ходам подачи, до GATE 2 не доходит.
Протокол: 10_REPEAT_CHECK.md, реестр repeat/REGISTRY.md.

ROUTE C:
06 → 09 → 08, если FACT-CHECK REQUIRED → 09 FINAL EDIT
если 06 выбрал самостоятельную карусель и передал
09 полный Carousel Brief.

ROUTE A для 09 не используется: это стандартный
non-carousel production route через 07.

Для non-carousel assets 09 = NOT_REQUIRED.

09 НЕ выбирает стратегию самостоятельно.

После завершения production и approval:

→ PUBLICATION
→ OWN PERFORMANCE DATA
→ 01
→ NEXT CYCLE.

Ни один downstream-модуль не должен молча изменять
стратегическое решение upstream-модуля.

7. SEARCH DEMAND ≠ REAL HUMAN DEMAND
==================================================

Низкий поисковый спрос не означает автоматически низкий реальный спрос.

Система различает:

1. QUANTITATIVE SEARCH DEMAND
2. QUALITATIVE DEMAND
3. SPECIALIST-SEEKING DEMAND
4. LATENT / HIDDEN DEMAND
5. UNDERSERVED DEMAND

Рабочая иерархия:

SEARCH
→
DISCUSSION
→
HELP-SEEKING
→
LATENT
→
UNDERSERVED

Отдельно существует:

PROBLEM DISCOVERY.

Это поиск проблем, которые человек:

— ещё не умеет назвать;
— формулирует через историю;
— описывает эвфемизмами;
— задаёт как «что со мной происходит?»;
— спрашивает «нормально ли это?»;
— не понимает, к кому обращаться;
— боится рассказать специалисту;
— не может найти подходящего специалиста.

Если количественный поисковый спрос не проверен:

DATA INSUFFICIENT.

Не делать вывод:

«низкий search volume = низкий спрос».


==================================================
8. НАУКА
==================================================

SCIENCE & DISCOVERY работает автономно.

Научный поиск НЕ ограничивается:

— темами спроса;
— вирусными темами;
— конкурентами;
— текущими контентными трендами.

Научный радар должен самостоятельно искать новое и важное на всей территории экспертизы.

Принцип:

СНАЧАЛА:

Что нового произошло в науке вообще?

ЗАТЕМ:

Есть ли этому контентное применение?

Приоритет:

— systematic reviews;
— meta-analyses;
— RCT;
— large cohort;
— longitudinal research;
— experimental studies;
— качественные исследования;
— другие релевантные первичные источники.

При возможности проверять первоисточник.

Если первоисточник не проверен:

PRIMARY SOURCE NOT VERIFIED.
Такой факт в контент не идёт.

ПРАВИЛО ИСТОЧНИКОВ (Татьяна, 14.10.2026, D-19):
«информация должна быть достоверная, без инфопиздеца».

1. Каждый научный факт и каждая цифра только по ПЕРВОИСТОЧНИКУ,
   не по пересказу (статья, обзор, СМИ, блог, чужой пост не годятся
   как источник цифры).
2. Проверка через коннекторы Consensus и PubMed: найти саму
   публикацию, сверить цифру, выборку, дизайн и вывод.
   Всё, что уходит на проверку, идёт в ветку «Проверка науки».
3. Не подтвердилось по первоисточнику: выкидываем или заменяем
   подтверждённым. PRIMARY SOURCE NOT VERIFIED в контент не идёт.

КНИГИ АВТОРОВ (Татьяна, 14.10.2026, D-19):
книги годятся как источник, но только по ОРИГИНАЛУ из открытого
доступа, не по пересказу, конспекту или переводу «по мотивам».
Цифру или тезис из книги подаём как «автор пишет в книге…»,
а не «исследование показало». Указываем автора, книгу, главу
или страницу. Книга не заменяет исследование там, где нужен
научный факт.

ПОЛЕ ПОИСКА (Татьяна, 14.10.2026, D-19):
философия, психология, социология, сексология.
Исследования по эндокринологии, урологии, гинекологии, андрологии
берём только в рамках её профиля: связь и общее влияние на психику,
секс и пару. Лечение, препараты, анализы, диагностика это
медицина, «не наша юрисдикция»: туда не лезем.

Подробности: 05 (разделы 3, 5, 6) и 08 (разделы 12, 41).

При этом:

HIGH AS EVIDENCE
≠
HIGH AS PRIORITY.

Высокая научная доказательность не означает автоматически высокий контентный приоритет.

Высокий viral signal не означает автоматически высокий клиентский потенциал.

Высокий спрос не означает автоматически высокую экспертную ценность.

11. CONTENT DIVERSITY
==================================================

ONE TOPIC ≠ ONE WEEK.

Одна тема может быть раскрыта в нескольких форматах.

Но система должна контролировать повторяемость смысла.

13. VOICE DNA
==================================================

Общий Voice DNA действует для всех текстовых протоколов, прежде всего 07 и 09.

кроме фактов и безопасности (раздел 48.14).

ГЛАВНОЕ ПРАВИЛО ВСЕХ ТЕКСТОВ (Татьяна, 09.10.2026):
карусели, подписи, Telegram, VK, Threads, сценарии Reels и сторис
пишутся так, как говорит Татьяна, чтобы текст и она на видео
были одним человеком: «чтобы не было такого, что текст отдельно,
а я отдельно».

РИТМ: без рубленых фраз с точкой на каждом шаге. Длинные,
сложные, слегка «рваные» предложения через запятые и придаточные,
как живая мысль; короткий удар отдельной строкой, не больше
одного на слайд (VOICE_PROFILE.md, раздел 15).

ЮМОР, САРКАЗМ, ТРОЛЛИНГ, МАТ: там, где уместно по смыслу,
дозированно, никогда для показухи. Мат одной точкой на текст,
не связкой; не на темах насилия, горя, болезни
(VOICE_PROFILE.md, раздел 6). В Instagram и Reels учитывать
риск модерации; финально решает Татьяна на GATE 2.

Основной язык:

РУССКИЙ.

Основное обращение:

«ты».

Язык:

— взрослый;
— прямой;
— интеллектуальный;
— точный;
— живой;
— иногда провокативный;
— разговорный, но не примитивный.

Естественные конструкции брать из её реальной речи
(VOICE_PROFILE.md, раздел 4): «Смотри», «Так вот», «Понимаешь?»,
«И да, и нет», быстрый поворот мысли, контраст через «но».
Банк оборотов это камертон, а не шаблон: три фирменных
оборота подряд уже пародия.

НЕ придумывать искусственные фирменные выражения.

Не использовать автоматически:

«давайте честно»;
«вот здесь самое интересное»;
«самое главное»;
«психологи давно доказали»;
«тело всегда знает правду»;
«всё из детства»;
«это ваша травма».

Текст должен звучать как естественная речь Татьяны.

Проверка:

Если убрать имя Татьяны, текст не должен легко принадлежать любому другому хорошему эксперту.

Если может принадлежать — переписать.

==================================================
ACTIVE PHOTO BANK
==================================================

ACTIVE PHOTO BANK = последняя утверждённая и актуальная
коллекция фотографий Татьяны.

ACTIVE содержит только текущий утверждённый набор.

ARCHIVE содержит предыдущие версии и старые наборы.

ARCHIVE НЕ используется автоматически.

При обновлении Photo Bank:

CURRENT ACTIVE
→ ARCHIVE

NEW APPROVED PHOTO SET
→ ACTIVE

В системе одновременно используется только один
ACTIVE PHOTO BANK.


==================================================
PHOTO BANK ACCESS
==================================================

ACTIVE PHOTO BANK является общим системным ресурсом.

Его могут использовать production-модули, которым
необходим персональный визуальный материал, в частности:

07 — CONTENT PRODUCER

09 — CAROUSEL BUILDER

Photo Bank не принадлежит 09.

07 и 09 получают доступ к ACTIVE PHOTO BANK
как к системному ресурсу в рамках соответствующей
визуальной задачи.

Другие production-модули могут использовать ACTIVE
PHOTO BANK только при наличии соответствующей
визуальной задачи.


==================================================
PHOTO SELECTION
==================================================

Production-модуль самостоятельно выбирает подходящую
фотографию из ACTIVE PHOTO BANK с учётом:

— content function;
— visual meaning;
— composition;
— facial expression;
— pose;
— continuity;
— visual system;
— current production brief.

Пользователь не обязан каждый раз вручную указывать
конкретную фотографию.


==================================================
PHOTO BANK SAFETY
==================================================

Не использовать фотографии из ARCHIVE автоматически.

Не смешивать ACTIVE и ARCHIVE без отдельного решения
пользователя.

Не использовать фотографию, если её визуальная
идентичность или актуальность не может быть надёжно
определена.

Если подходящего визуального материала в ACTIVE PHOTO BANK
нет:

DATA INSUFFICIENT

или

NEW VISUAL REQUIRED.

Система не должна произвольно выбирать старую фотографию
из ARCHIVE только потому, что в ACTIVE нет подходящего
материала.


==================================================
PHOTO BANK UPDATE
==================================================

Обновление Photo Bank считается изменением системного
визуального ресурса.

После обновления:

— новый набор становится ACTIVE;
— предыдущий ACTIVE становится ARCHIVE;
— production-модули используют новый ACTIVE
  при следующих задачах.

==================================================
26. CAROUSEL STRUCTURE LOCK
==================================================

06/07 передают 09 не только тему и текст, а STRUCTURE MAP.

Минимум:

S01 — функция / hook
S02 — recognition / problem
S03 — differentiation
S04 — mechanism / explanation
S05 — important limitation or distinction
S06 — context / example
S07 — evidence, если требуется
S08 — nuance / reframe
S09 — implication / practical meaning
S10 — conclusion / CTA

Это НЕ обязательная структура каждого материала.

Но для DEEP-карусели production brief обязан явно определить
функцию каждого слайда.

Нельзя создавать два или более слайда с одинаковой функцией,
если это не оправдано содержанием.

Каждый слайд должен добавлять новую смысловую единицу,
новый контекст, доказательство, различение или необходимый
переход.


==================================================
27. INFORMATION DENSITY LOCK
==================================================

INFORMATION UNIT = самостоятельная смысловая единица,
которую можно сформулировать как отдельное содержательное
утверждение, различение, механизм, пример, ограничение,
доказательство или вывод.

Минимальный TARGET:

SHORT:
4–5 information units

STANDARD:
6–8

DEEP:
8–12

LONGFORM:
12+

Минимум является production floor, а не обязательной
целевой длиной.

Если материал требует меньше содержания, DEPTH должен быть
понижен до соответствующего уровня.

Нельзя оставлять DEEP только потому, что визуально «красиво».

Если TARGET не достигнут:

CAROUSEL STATUS = NOT READY.


==================================================
28. DEPTH CONTRACT
==================================================

SHORT:
одна основная мысль + минимальное развитие.

STANDARD:
основная мысль + объяснение + различение / контекст.

DEEP:
основная мысль + механизм + различения + контекст +
evidence/limitation при необходимости + implication.

LONGFORM:
расширенное многослойное объяснение с несколькими
самостоятельными смысловыми блоками.

09 НЕ имеет права самостоятельно снижать DEPTH,
если это меняет стратегическое решение 06.

Если объём не помещается в выбранный формат:

— пересобрать структуру;
— изменить slide count в пределах approved brief;
— запросить production revision;
— либо вернуть на strategy revision.

Нельзя решать проблему сокращением экспертного содержания
без фиксации revision.

==================================================
31. EVIDENCE PRESERVATION LOCK
==================================================

Если 07 или 09 использует:

— научный результат;
— статистику;
— медицинский факт;
— причинное утверждение;
— количественную оценку;
— клиническое утверждение;

— исходную силу утверждения;
— необходимую квалификацию;
— ограничения;
— distinction correlation / causation;
— source linkage.

09 не имеет права усиливать claim ради «сильного слайда».

Нельзя:

association → cause

finding → recommendation

single study → consensus

research concept → diagnosis.

Если claim изменён по смыслу:

→ 08 FACT CHECKER.

Если evidence потеряно при сборке:

CAROUSEL STATUS = NOT READY.


==================================================
32. CAROUSEL VISUAL RULES
==================================================

Визуальная система должна поддерживать содержание,
а не заменять его.

T01 — DARK EXPERT / EDITORIAL:
— тёмная редакционная база;
— высокая контрастность;
— экспертный editorial характер;
— строгая типографика.

T02 — SOFT EXPERT / CLINICAL EDITORIAL:
— более мягкая экспертная подача;
— спокойная клиническая визуальная логика;
— отсутствие декоративной «женскости».

T03 — DIGITAL / SCREEN / SYSTEM:
— интерфейсная / цифровая логика;
— экранные элементы;
— системные блоки;
— визуальная структура данных / сообщений.

Конкретные размеры, шрифты, сетки и reference должны
браться из утверждённого TEMPLATE ASSET.

Если reference отсутствует:

TEMPLATE ASSET = NOT VERIFIED
→ BLOCKED.

==================================================
HUMAN APPROVAL GATES
==================================================

Автоматизация НЕ отменяет человеческое решение
Татьяны в критических точках.

Обязательные approval gates:

GATE 1 — STRATEGY APPROVAL

06 формирует STRATEGY DECISION.
До запуска production конкретное стратегическое решение
должно иметь явное человеческое решение Татьяны:

APPROVE
APPROVE AS TEST
REJECT
REQUEST REVISION

Терминальные решения GATE 1:
APPROVE
APPROVE AS TEST
REJECT

Нетерминальное решение:
REQUEST REVISION

APPROVE AS TEST является формой человеческого approval.

Система НЕ имеет права самостоятельно переводить
стратегическое решение в TEST для обхода GATE 1.

При APPROVE AS TEST фиксируется:

PUBLICATION MODE = TEST

Это не отменяет ни GATE 2, ни FACT CHECK, ни другие
обязательные этапы.

GATE 2 — FINAL CONTENT APPROVAL

После завершения всех обязательных production stages
конкретного asset он получает:

ASSET STATE = AWAITING_HUMAN_APPROVAL

и

FINAL APPROVAL STATUS = PENDING.

Для Route A финальный production path завершается
после 07 FINAL EDIT и, если требуется,
VISUAL_PRODUCTION.

Для Route B финальный production path завершается
после 09 CAROUSEL BUILD.

Для Route C финальный production path завершается
после 09 FINAL EDIT.

Татьяна может:

APPROVE
REJECT
REQUEST REVISION

При APPROVE:

FINAL APPROVAL STATUS = APPROVED

и asset может перейти в:

READY_TO_PUBLISH.

При REJECT или REQUEST REVISION:
FINAL APPROVAL STATUS = NOT_READY
до завершения новой production / final edit и нового GATE 2.

При REJECT или REQUEST REVISION asset возвращается
на последний валидный production stage в соответствии
с route.

При таком возврате:
FINAL APPROVAL STATUS = NOT_READY.

До возврата система обязана классифицировать причину revision:

PRODUCTION_REVISION
— меняется production execution, wording, structure, visual или
другая downstream-деталь, но утверждённая стратегия сохраняется.

STRATEGY_REVISION
— меняется audience, strategic angle, primary function, format
или другой параметр утверждённой стратегии.

STRATEGY_REVISION дополнительно классифицируется как:

ASSET_LOCAL
— стратегически изменяется только конкретный asset;
другие assets и общий production plan не затрагиваются.

CYCLE_WIDE
— изменение затрагивает общий production/publication plan
или несколько зависимых assets.

Для PRODUCTION_REVISION маршрут остаётся внутри текущего route.
Для STRATEGY_REVISION выполняется:

ASSET → 06 RETURN TO STRATEGY
→ NEW STRATEGY DECISION ID
→ GATE 1
→ соответствующий production route.

Если STRATEGY_REVISION = ASSET_LOCAL, CYCLE STATE не обязан
возвращаться в STRATEGY; unaffected assets могут продолжать
свои независимые states, если нет общей зависимости.

Если STRATEGY_REVISION = CYCLE_WIDE, затронутые assets
приостанавливаются, CYCLE STATE возвращается в STRATEGY,
и после нового GATE 1 перестраивается только затронутая
часть downstream-пути. Unaffected assets могут продолжать работу
только если новая стратегия не меняет их зависимости или общий план.

После завершения обязательной доработки asset снова должен
достичь AWAITING_HUMAN_APPROVAL с FINAL APPROVAL STATUS = PENDING.
Только после нового APPROVE asset может перейти в READY_TO_PUBLISH.

GATE 2 STRATEGY-REVISION RULE

Если human decision на GATE 2 изменяет не production execution,
а стратегические параметры approved decision, GATE 2 не может
самостоятельно менять strategy внутри 07 или 09.

В таком случае используется только:

GATE 2
↓
STRATEGY REVISION SCOPE
↓
ASSET_LOCAL или CYCLE_WIDE
↓
06
↓
NEW STRATEGY DECISION ID
↓
NEW GATE 1
↓
DOWNSTREAM PRODUCTION.

Старый STRATEGY DECISION ID не переписывается и не редактируется
задним числом.

GATE 3 — PUBLICATION EVENT

Это не дополнительный human approval gate.
Это контрольная точка фиксации факта публикации.

Публикация считается выполненной только после фиксации
факта публикации в CYCLE RECORD.

Система НЕ должна считать material опубликованным
только потому, что production или approval завершены.

Если после FACT CHECK, FINAL EDIT или CAROUSEL BUILD
появляется новый проверяемый claim либо существенно
изменяется уже проверенный claim, asset обязан вернуться
в 08 до повторного GATE 2.

DEMAND SIGNAL

COMPETITOR SIGNAL
VIRAL DNA
SCIENCE
OWN PERFORMANCE
EXPERTISE
CLIENT VALUE

DATA INSUFFICIENT

HYPOTHESIS / TEST

Отсутствие необязательного источника не делает решение

==================================================
46. CYCLE / ASSET STATE & CYCLE MANAGEMENT
==================================================

TATIANA CONTENT OS работает циклическими итерациями.

Каждый рабочий цикл получает:

CYCLE ID

и дополнительный уникальный:

CYCLE RUN ID

CYCLE ID — человекочитаемый идентификатор цикла.
CYCLE RUN ID — технически уникальный immutable identifier
конкретного запуска.

Формат CYCLE ID:

YYYY-MM-DD-CYCLE-###

### — последовательный номер цикла в рамках даты.

Пример:

2026-10-05-CYCLE-001

CYCLE RUN ID должен быть уникальным даже при повторном
или параллельном запуске automation.

Если техническая реализация не предоставляет атомарный
счётчик, CYCLE ID не используется как единственный
уникальный технический идентификатор.

CYCLE ID и CYCLE RUN ID НЕ переиспользуются.


==================================================
CYCLE STATE
==================================================

CYCLE STATE описывает состояние ВСЕГО рабочего цикла.

Он НЕ описывает состояние отдельного content asset.

Допустимые состояния цикла:

NEW

RESEARCHING

STRATEGY

PRODUCTION

PUBLICATION

LEARNING

CLOSED

Базовая последовательность:

NEW
↓
RESEARCHING
↓
STRATEGY
↓
PRODUCTION
↓
PUBLICATION
↓
LEARNING
↓
CLOSED

CYCLE STATE является агрегированным control-state цикла.
Он не обязан совпадать со state каждого отдельного asset.

Assets внутри одного цикла могут одновременно находиться
на разных production stages. Asset State является источником
правды для конкретного материала, а CYCLE STATE показывает
текущую управляющую фазу всего цикла.

Если один asset возвращается из PRODUCTION в STRATEGY, сначала
определяется STRATEGY REVISION SCOPE.

При ASSET_LOCAL другой независимый asset может продолжать свой
текущий state и при наличии READY_TO_PUBLISH может быть опубликован,
даже если CYCLE STATE ещё находится в PRODUCTION.

При CYCLE_WIDE затронутые assets приостанавливаются, а CYCLE STATE
возвращается в STRATEGY. Unaffected assets могут продолжать только
если новая стратегия не меняет их зависимости, общий publication plan
или обязательные outputs цикла.

CYCLE STATE не является блокировкой всех asset states автоматически.

CYCLE STATE меняется только тогда, когда выполнены условия
перехода на уровне всего цикла.

--------------------------------------------------
CYCLE STATE TRANSITION RULES
--------------------------------------------------

NEW → RESEARCHING

Когда цикл официально запущен.

RESEARCHING → STRATEGY

Когда необходимые для стратегических решений research outputs
получены или явно отмечены как DATA INSUFFICIENT / NOT_AVAILABLE,
и 06 может принять решения без скрытого отсутствия данных.

STRATEGY → PRODUCTION

Только после того, как все запланированные STRATEGY DECISION ID
получили ТЕРМИНАЛЬНОЕ решение GATE 1:

APPROVE
APPROVE AS TEST
или
REJECT.

REQUEST REVISION НЕ является терминальным решением.
При REQUEST REVISION CYCLE STATE остаётся STRATEGY,
а конкретное решение возвращается в 06 до новой редакции
и нового GATE 1 approval.

REJECT и окончательно исключённые decisions
не создают production assets.

Если после GATE 1 все решения имеют статус REJECTED
и ни одного production asset не создано, цикл может перейти
напрямую:

STRATEGY → LEARNING

с фиксацией PUBLICATION = NOT_REQUIRED.

ASSET-LEVEL PUBLICATION DURING PRODUCTION

Конкретный READY_TO_PUBLISH asset может быть опубликован отдельно
до перехода всего цикла в CYCLE STATE = PUBLICATION, если:

— GATE 2 APPROVED;
— обязательные checks этого asset завершены;
— публикация не зависит от незавершённой стратегии другого asset;
— publication plan не изменён CYCLE_WIDE revision.

Это не переводит весь CYCLE STATE автоматически в PUBLICATION.

PRODUCTION → PUBLICATION

Только когда для всех активных assets текущего цикла:

— production завершён;
— обязательный fact-check завершён;
— обязательная final edit завершена;
— обязательный visual production завершён;
— carousel build завершён, если он нужен;
— каждый asset, предназначенный к публикации, находится
  в READY_TO_PUBLISH или PUBLISHED;
— остальные assets явно CANCELLED или NOT_REQUIRED
  в соответствии с правилами closure.

Наличие одного опубликованного asset НЕ переводит цикл
в PUBLICATION, если другие активные assets ещё находятся
в production.

PUBLICATION → LEARNING

Когда публикационные действия текущего цикла завершены
или явно закрыты, а цикл переходит к анализу результатов.

LEARNING → CLOSED

Когда learning record создан, открытые вопросы и blockers
зафиксированы, CYCLE OUTCOME определён, и нет необходимости
оставлять цикл открытым.

--------------------------------------------------
CYCLE-LEVEL BACKWARD TRANSITION
--------------------------------------------------

PRODUCTION → STRATEGY

Допускается только тогда, когда downstream-return требует
изменения strategic angle, audience, format, primary function
или иного параметра утверждённой стратегии.

При таком возврате:
— соответствующий asset прекращает текущий downstream route;
— STRATEGY DECISION возвращается в 06;
— GATE 1 должен быть пройден заново;
— downstream production продолжится только после нового approval.

Если для нового стратегического решения нужны дополнительные
исследовательские данные, сначала выполняется соответствующий
research return в RESEARCHING, после чего цикл снова переходит
в STRATEGY.

Публикационные и learning-состояния не возвращаются автоматически
в предыдущие cycle states после CLOSED.


==================================================
CYCLE BLOCKING
==================================================

BLOCKED НЕ является обычным CYCLE STATE.

BLOCKED — отдельное состояние блокировки, которое фиксируется
в BLOCKER RECORD.

Один заблокированный asset не делает автоматически весь цикл
BLOCKED.

Если часть assets может продолжать работу, они продолжают её.

Каждая блокировка должна иметь:

BLOCKER ID
CYCLE ID
CYCLE RUN ID
REASON
AFFECTED MODULE
AFFECTED ASSET, если применимо
DATE
REQUIRED ACTION
OWNER / RESPONSIBLE SIDE
STATUS
RESOLUTION

При снятии blocker конкретный asset или модуль возвращается
к последнему валидному состоянию.

Он НЕ возвращается автоматически в NOT_STARTED.


==================================================
CONTENT / ASSET STATE
==================================================

CONTENT / ASSET STATE описывает состояние КАЖДОГО
отдельного content asset.

Каждый asset имеет собственный CONTENT ASSET ID.

Основные состояния:

NOT_STARTED

PRODUCTION

FACT_CHECK

FINAL_EDIT

CAROUSEL_BUILD

VISUAL_PRODUCTION

AWAITING_HUMAN_APPROVAL

READY_TO_PUBLISH

PUBLISHED

Дополнительные состояния:

BLOCKED

CANCELLED

--------------------------------------------------
ASSET STATE MEANING
--------------------------------------------------

NOT_STARTED

Asset запланирован, но production ещё не начат.

PRODUCTION

Asset находится в основном production process
originating module.

FACT_CHECK

Asset version проходит обязательную проверку 08.

FINAL_EDIT

Осуществляется финальная редакция модуля, который отвечает
за текущую проверяемую version.

Обычно это originating producer 07 или 09.
В Route B стандартная final edit перед CAROUSEL_BUILD выполняется 07.
Если после CAROUSEL_BUILD новая проверка 08 выявила изменение,
внесённое 09, final edit для этой version выполняется 09.

CAROUSEL_BUILD

09 выполняет specialized carousel production
для Route B.

VISUAL_PRODUCTION

В Route A выполняется отдельное visual production,
если это явно требуется.

AWAITING_HUMAN_APPROVAL

Все обязательные production stages завершены,
но GATE 2 ещё не получил окончательного human decision.

READY_TO_PUBLISH

GATE 2 пройден с APPROVED.
Asset может быть опубликован.

PUBLISHED

Факт публикации зафиксирован.

BLOCKED

Текущий route временно не может продолжаться.

CANCELLED

Запланированный asset прекращён и больше не должен
продолжаться без нового отдельного решения.

— Route B на Route C;
— Route C на Route A;

без возврата решения в 06 и нового GATE 1 approval.

Если изменился формат настолько, что asset фактически
становится другим production type, создаётся:

STRATEGY REVISION

или новый CONTENT ASSET ID — в зависимости от масштаба изменения.

Нельзя тихо менять route внутри production.

==================================================
FACT-CHECK REQUIREMENT
==================================================

Каждый asset получает начальный:

FACT-CHECK REQUIREMENT

Допустимые значения:

REQUIRED
NOT_REQUIRED

Это минимальное production condition.

Если FACT-CHECK REQUIREMENT = REQUIRED,
asset обязан пройти 08 до publication.

Если FACT-CHECK REQUIREMENT = NOT_REQUIRED,
asset может изначально не проходить 08.

Но NOT_REQUIRED НЕ является постоянным запретом на fact-check.


==================================================
FACT-CHECK ESCALATION RULE
==================================================

Если в любой production stage появляется хотя бы один
новый или изменённый checkable claim, FACT-CHECK REQUIREMENT
автоматически становится:

REQUIRED

Если claim появился после уже завершённого FACT_CHECK,
asset возвращается в 08, а затем продолжает route с того
production stage, который обязан реализовать correction.
Для Route A это 07 FINAL_EDIT с последующим
VISUAL_PRODUCTION, если он требуется. Для Route B post-carousel
это 09 FINAL_EDIT. Для Route C это 09 FINAL_EDIT.

Asset не может перейти к AWAITING_HUMAN_APPROVAL,
READY_TO_PUBLISH или PUBLISHED, пока обязательный
FACT_CHECK не завершён.

Checkable claim включает, в частности:

— scientific claim;
— medical claim;
— psychological claim presented as factual;
— statistical claim;
— prevalence/risk claim;
— diagnostic claim;
— causal claim;
— efficacy claim;
— physiological mechanism claim;
— guideline/recommendation claim;
— classification claim;
— numerical result attributed to research.

Если 07 или 09 не уверены, является ли формулировка
checkable claim, применяется:

FACT-CHECK REQUIRED.

Downgrade REQUIRED → NOT_REQUIRED после начала
fact-check запрещён для текущей version.

==================================================
ASSET STATE INTEGRITY
==================================================

Нельзя:

— переводить asset в FACT_CHECK, если fact-check NOT_REQUIRED
  и не сработал FACT-CHECK ESCALATION;
— переводить asset в CAROUSEL_BUILD, если asset не является carousel
  и не проходит Route B;
— переводить asset в VISUAL_PRODUCTION, если
  SEPARATE VISUAL PRODUCTION REQUIREMENT = NOT_REQUIRED;
— переводить asset в READY_TO_PUBLISH без APPROVED human decision;
— считать asset AWAITING_HUMAN_APPROVAL, если обязательный
  fact-check не завершён;
— считать asset AWAITING_HUMAN_APPROVAL, если обязательная
  final edit не завершена;
— считать Route B asset AWAITING_HUMAN_APPROVAL,
  если CAROUSEL_BUILD не завершён;
— считать PUBLISHED без зафиксированного факта публикации;
— считать asset completed только потому, что существует файл.

READY_TO_PUBLISH всегда означает:

FINAL PRODUCTION COMPLETE
+
MANDATORY CHECKS COMPLETE
+
GATE 2 APPROVED.

==================================================
ASSET BLOCKED / CANCELLED / NOT_REQUIRED
==================================================

NOT_REQUIRED означает:

asset или конкретный production stage не был нужен
и никогда не должен считаться незавершённым.

CANCELLED означает:

asset был запланирован, но позже прекращён.

NOT_REQUIRED и CANCELLED НЕ являются взаимозаменяемыми.

Если запланированный asset отменён после включения
в утверждённый production plan, его cancellation должно
быть явно зафиксировано.

Такой asset НЕ считается автоматически выполненным.

Он влияет на CYCLE OUTCOME как незавершённый output,
если только стратегия не была официально пересмотрена,
asset не исключён из плана через новый GATE 1 decision,
или его функция не заменена другим approved asset.

BLOCKED означает, что конкретный asset не может
продолжить текущий route без устранения причины.

Если blocker снят, asset возвращается на последний
валидный state route.

Определения:

NOT_REQUIRED
— модуль не нужен текущему циклу вообще.

IN_PROGRESS
— у модуля есть активная незавершённая работа.

PARTIALLY_COMPLETED
— модуль уже завершил часть своих outputs,

COMPLETED
— все требуемые outputs модуля в текущем цикле завершены.

BLOCKED
— модуль не может продолжить ключевую работу.

NEEDS_REVIEW

отдельный content output.

carousel assets для Route B или Route C.

08 получает NOT_REQUIRED только если ни один active asset/version
текущего цикла не требует fact-check.

==================================================
VERSIONING & IMMUTABILITY
==================================================

STRATEGY DECISION ID:
— immutable;
— не редактируется задним числом;
— любое существенное изменение стратегии создаёт новый ID.

STRATEGY DECISION VERSION:
— номер revision внутри одной strategic lineage;
— увеличивается при создании нового decision на основании предыдущего;
— всегда сопровождается PARENT STRATEGY DECISION ID.

CONTENT ASSET ID:
— идентификатор конкретного content asset;
— сохраняется при downstream revision, если стратегия остаётся той же.

ASSET VERSION:
— увеличивается при каждом material change конкретного asset
до публикации;
— пример: v1 → v2 → v3 → FINAL.

После публикации PUBLISHED version является исторической
и не перезаписывается.

Если требуется изменить опубликованный material,
создаётся новая ASSET VERSION с новым human approval
и новым fact-check, если claims изменены.

Если изменение настолько существенно, что меняется стратегия,
audience, primary function или format:
— создаётся новый STRATEGY DECISION ID;
— создаётся новая STRATEGY DECISION VERSION;
— создаётся новый CONTENT ASSET ID, если меняется content object;
— старый asset и decision сохраняются как исторические.

PLATFORM VERSION может иметь собственную редакционную адаптацию.
Если адаптация меняет checkable claim, применяется
FACT-CHECK ESCALATION RULE.

==================================================
NO DUPLICATE WORK
==================================================

Система не должна автоматически повторять завершённый
этап без основания.

Повторный запуск допускается только если:

— изменились входные данные;
— появился новый период исследования;
— обнаружена ошибка;
— предыдущий результат получил статус NEEDS_REVIEW;
— пользователь запросил переработку;
— downstream-модуль обнаружил проблему, требующую
  возврата upstream;
— создана новая ASSET VERSION.

Опубликованная версия не перезаписывается.


==================================================
BACKWARD RETURN
==================================================

Если downstream-модуль обнаруживает проблему,
он не исправляет стратегическое решение самостоятельно.

Он возвращает задачу upstream-модулю.

Примеры:

08 → 07
если проблема обнаружена в material стандартного Route A
или в Route B ДО CAROUSEL BUILD;

08 → 09
если проблема обнаружена в standalone carousel Route C
или в Route B ПОСЛЕ CAROUSEL BUILD, когда проверяемую
версию изменил 09;

09 → 07
если Route B carousel build невозможно корректно выполнить
без возврата к production material 07;

07 → 06
если production brief невозможно выполнить без изменения
стратегической идеи;

09 → 06 через RETURN TO STRATEGY,
если проблема настолько существенна, что меняет
стратегический angle, audience, format или primary function.

Для Route B:

06 → 07 → 08 → 07 FINAL EDIT → 09

Для Route C:

06 → 09 → 08 → 09 FINAL EDIT

При возврате фиксируется:

RETURN FROM
RETURN TO
REASON
AFFECTED CONTENT
AFFECTED ASSET VERSION
REQUIRED REVISION

Если возврат меняет стратегическое решение,
GATE 1 должен быть пройден заново.


==================================================
CYCLE OUTCOME
==================================================

CYCLE OUTCOME фиксирует результат завершения цикла.

Допустимые значения:

COMPLETED

PARTIALLY_COMPLETED

CLOSED_WITH_BLOCKERS

CANCELLED

COMPLETED:

Все outputs, которые остаются обязательными в финальном
утверждённом плане цикла, завершены.

Каждый asset должен быть:

PUBLISHED

или

NOT_REQUIRED

в соответствии с правилами plan revision.

CANCELLED asset сам по себе не становится COMPLETED.

Если отменённый asset был официально заменён другим
approved asset или через GATE 1 исключён из финального плана,
это должно быть отражено в cycle record.

PARTIALLY_COMPLETED:

Часть запланированных outputs завершена,
часть не завершена или была отменена,
но цикл закрывается осознанным решением.

CLOSED_WITH_BLOCKERS:

Цикл закрыт при наличии нерешённых blockers,
которые не позволяют считать все обязательные
outputs выполненными.

CANCELLED:

Отменён весь цикл, а не только отдельный asset.

CYCLE OUTCOME НЕ заменяет ASSET STATE.

Каждый asset сохраняет своё фактическое состояние.

Правила присвоения outcome:

COMPLETED
— все обязательные outputs завершены, required assets
  получили необходимые approvals, а публикация либо выполнена,
  либо обоснованно NOT_REQUIRED; незакрытых обязательных blockers нет.

PARTIALLY_COMPLETED
— цикл закрыт осознанным решением при наличии невыполненных
  или отменённых outputs, но без состояния, которое должно быть
  классифицировано как CLOSED_WITH_BLOCKERS.

CLOSED_WITH_BLOCKERS
— цикл закрывается при наличии нерешённых blockers,
  препятствующих полному завершению обязательных outputs.

CANCELLED
— отменён весь цикл.


==================================================
CYCLE STATE STORAGE
==================================================

Состояние текущего цикла и история завершённых циклов
являются логическим системным ресурсом TATIANA CONTENT OS.

Физический способ хранения этого состояния определяется
технической automation / workspace implementation.

Нельзя считать Library автоматически базой данных,
state machine или гарантированным хранилищем automation state
только на основании наличия файлов.

Если техническая реализация использует Library,
это должно быть реализовано и проверено отдельно.

Логическая структура:

CURRENT CYCLE STATE
+
CURRENT CYCLE RECORD
+
HISTORY

CURRENT содержит запись активного цикла.

HISTORY содержит итоговые записи завершённых циклов.

Завершённые циклы не перезаписываются текущими данными.

Текущий цикл не должен автоматически смешиваться
с историей предыдущих циклов.


==================================================
CYCLE CLOSURE
==================================================

CYCLE STATE может перейти в CLOSED только после
явного решения о завершении текущего цикла.

Перед закрытием должны быть проверены:

— обязательные outputs текущего цикла;
— состояния всех CONTENT ASSETS;
— наличие незакрытых BLOCKED assets;
— наличие CANCELLED assets и причины cancellation;
— fact-check для материалов, которым он необходим;
— final edit для материалов, которым он необходим;
— visual production для Route A assets, которым он необходим;
— carousel build для Route B assets;
— human approval для материалов, предназначенных
  к публикации;
— факт публикации или обоснованный NOT_REQUIRED
  в соответствии с финальным планом;
— доступные performance data;
— learning record;
— открытые вопросы;
— blockers;
— CYCLE OUTCOME.

Нельзя считать цикл COMPLETED только потому,
что часть assets опубликована.

После CLOSED цикл не изменяется автоматически.

==================================================
47. REGRESSION CONTROL / CHANGE MANAGEMENT
==================================================

Этот раздел существует для того, чтобы система не возвращалась
к уже исправленным архитектурным ошибкам.

Любое будущее изменение MASTER PROTOCOL должно проходить
полный regression audit до выдачи новой версии.

НЕЛЬЗЯ исправлять master protocol локальным patch без проверки
всех зависимых разделов.

Если меняется архитектурный блок целиком, новая версия должна
выдаваться как полный файл, а не как набор отдельных кусков.

Перед каждой новой версией обязательны следующие проверки:

1. ROLE AUDIT

Проверить, что каждый модуль имеет одну определённую роль
и не забирает функцию другого модуля.

2. DEPENDENCY AUDIT

Проверить все FROM → TO связи, включая backward returns.

3. ROUTE AUDIT

Проверить все production routes:

ROUTE A — 07
ROUTE B — 07 → 09
ROUTE C — 09

Проверить каждый route минимум в двух вариантах:

FACT-CHECK REQUIRED
FACT-CHECK NOT_REQUIRED

Для Route A дополнительно проверить:

SEPARATE VISUAL PRODUCTION REQUIRED
SEPARATE VISUAL PRODUCTION NOT_REQUIRED

4. STATE AUDIT

Проверить отдельно:

CYCLE STATE
CONTENT / ASSET STATE
MODULE STATUS
HUMAN APPROVAL STATUS
CYCLE OUTCOME

Ни один state одной сущности не должен использоваться
как state другой сущности без явного определения.

5. GATE AUDIT

Проверить:

GATE 1 — STRATEGY APPROVAL
GATE 2 — FINAL HUMAN APPROVAL
GATE 3 — PUBLICATION EVENT

Проверить, что APPROVE AS TEST не отменяет GATE 2.
Проверить, что GATE 3 не ошибочно интерпретируется как дополнительный
human approval вместо фиксации publication event.

6. FACT-CHECK AUDIT

Проверить:

— обязательный fact-check;
— escalation при появлении нового checkable claim;
— возврат к originating producer;
— повторную проверку изменённого claim;
— запрет publication без обязательной проверки.

7. CAROUSEL AUDIT

Проверить, что 09:

— не является универсальным модулем;
— не выбирает стратегию;
— не добавляет новые claims без проверки;
— корректно работает в Route B;
— корректно работает в Route C;
— не создаёт лишний VISUAL_PRODUCTION state.

8. ID / VERSION AUDIT

Проверить связь:

CYCLE ID
→ CYCLE RUN ID
→ STRATEGY DECISION ID
→ CONTENT FAMILY ID
→ CONTENT ASSET ID
→ ASSET VERSION
→ PLATFORM VERSION

Fact-check должен быть привязан к конкретной проверенной
ASSET VERSION или PLATFORM VERSION.

9. EVIDENCE AUDIT

Проверить, что evidence requirements являются conditional,
а не универсальными.

Отсутствие необязательного источника не должно автоматически
делать стратегическое решение недействительным.

10. CLOSURE AUDIT

Проверить, что CYCLE OUTCOME соответствует фактическому
состоянию всех обязательных outputs.

COMPLETED нельзя присваивать циклу, если обязательный asset
остаётся незавершённым.

11. DUPLICATE-WORK AUDIT

Проверить, что система не запускает повторно уже завершённый
этап без новой причины, новой версии, новых данных или
явного запроса на revision.

12. STALE-TEXT AUDIT

Проверить весь файл на остатки предыдущей архитектуры,
включая: старые state names, старые route chains, старые
обязательные этапы и старые определения ролей.

13. CONTRADICTION AUDIT

Проверить каждое утверждение типа:

«обязательно»
«никогда»
«только»
«всегда»
«не требуется»

на наличие исключений в других разделах.

14. USER-INTENT AUDIT

Проверить, что изменения сохраняют уже утверждённые
пользовательские решения и не заменяют их собственной
интерпретацией системы.

15. FULL-FILE REGENERATION RULE

Если результат аудита требует изменения архитектурного блока,
не выдавать пользователю patch как финальную версию.

Только после этого выдавать его пользователю.

16. STATE-MACHINE EXECUTION AUDIT

Перед RELEASE необходимо выполнить сценарный прогон

ROUTE A × FACT-CHECK REQUIRED / NOT_REQUIRED
ROUTE A × VISUAL REQUIRED / NOT_REQUIRED
ROUTE A × claim escalation in PRODUCTION
ROUTE A × claim escalation in FINAL_EDIT
ROUTE A × claim escalation in VISUAL_PRODUCTION
ROUTE B × FACT-CHECK REQUIRED / NOT_REQUIRED

ROUTE B × 09 → 07 upstream correction
ROUTE C × FACT-CHECK REQUIRED / NOT_REQUIRED

ALL DECISIONS REJECTED
PARALLEL ASSETS WITH ONE LOCAL REVISION
PARALLEL ASSETS WITH ONE CYCLE-WIDE REVISION

Для каждого сценария необходимо доказать:
— допустимый исходный state;
— допустимый следующий state;

STRATEGY DECISION ID ↔ VERSION LINEAGE

READY_TO_PUBLISH ↔ GATE 2 APPROVED
PUBLISHED ↔ PUBLICATION EVENT
CLOSED ↔ CYCLE OUTCOME + REQUIRED OUTPUTS
