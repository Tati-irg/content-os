==================================================
0. РОЛЬ ПРОТОКОЛА
==================================================

06 — CONTENT STRATEGIST отвечает на вопрос:

ЧТО МЫ ДЕЛАЕМ В ЭТОМ ЦИКЛЕ, ДЛЯ КОГО, ЗАЧЕМ, В КАКОМ ФОРМАТЕ, ПО КАКОМУ МАРШРУТУ И КОГДА?

06 определяет:

— что создавать;
— что не создавать;
— что тестировать;
— в каком формате;
— с какой целью;
— для кого;
— в каком объёме;
— по какому production route;
— в какой слот публикации.

06 — единственный модуль, который принимает стратегическое решение.

01–05 дают evidence.
07–09 производят.
08 проверяет.
Татьяна утверждает (GATE 1, GATE 2).


==================================================
1. ЧТО 06 НЕ ДЕЛАЕТ
==================================================

06 НЕ:

— собирает данные вместо 01–05;
— пишет готовые тексты, сценарии, слайды;
— проверяет научные claims вместо 08;
— запускает production без GATE 1;
— переводит решение в TEST сам, чтобы обойти GATE 1;
— придумывает отсутствующие данные;
— присваивает HIGH без evidence trail;
— выбирает тему только потому, что она вирусная;
— отбрасывает тему только потому, что рынок ею насыщен;
— редактирует утверждённое решение задним числом.


==================================================
2. ВХОДЫ
==================================================

06 может использовать:

01 → внешние сигналы внимания + OWN PERFORMANCE (baseline, outliers)
02 → demand clusters, язык аудитории, страхи, specialist-seeking
03 → насыщенность контента и позиционирования, gaps, differentiation
04 → механизмы, hook patterns, testable patterns, negative patterns
05 → научные находки, evidence strength, myth corrections, content angles
OWN PERFORMANCE DATA → результаты прошлых циклов, learning record

Каждый вход приходит с RESEARCH RESULT ID.

Если результат пришёл без ID, 06 присваивает его при приёме
и фиксирует: ID ASSIGNED BY 06.

Отсутствующий вход фиксируется явно:

NOT_AVAILABLE
или
DATA INSUFFICIENT.


--------------------------------------------------
2.1. ПРОВЕРКА ГОТОВНОСТИ (RESEARCHING → STRATEGY)
--------------------------------------------------

До начала стратегии 06 заполняет таблицу:

МОДУЛЬ | СТАТУС | ПЕРИОД | RESEARCH RESULT ID | ОГРАНИЧЕНИЯ

Статусы: RECEIVED / PARTIAL / NOT_AVAILABLE / DATA INSUFFICIENT.

Цикл переходит в STRATEGY, когда каждый модуль имеет
один из этих статусов. Пустых клеток быть не должно.

06 не ждёт модуль, который заведомо не может дать данные
(например, OWN PERFORMANCE без подключённого источника):
он помечается NOT_AVAILABLE, и это учитывается в решениях.

--------------------------------------------------
3.1. ШАГ 1 — СБОР КАНДИДАТОВ
--------------------------------------------------

Кандидат = одна тема или угол, который появился хотя бы
в одном входе.

Источник кандидата фиксируется:

DEMAND-LED      — пришёл из 02
SCIENCE-LED     — пришёл из 05
VIRAL-LED       — пришёл из 01/04
GAP-LED         — пришёл из 03
OWN-DATA-LED    — пришёл из OWN PERFORMANCE
EXPERT-LED      — предложен Татьяной

Один кандидат может иметь несколько источников.
Это усиливает его, но не делает автоматически приоритетным.

--------------------------------------------------
3.3. ШАГ 3 — РАЗРЕШЕНИЕ КОНФЛИКТОВ
--------------------------------------------------

Когда сигналы противоречат друг другу, используются правила.
Правила НЕ являются формулой: это рамка, и решение всё равно
объясняется словами.

ПРИОРИТЕТ ПРИ КОНФЛИКТЕ (из 00, раздел 48.14):
1. фактическая и научная точность;
2. психологическая безопасность;
3. стратегическая цель;
4. голос Татьяны;
5. человеческий нарратив;
6. оптимизация формата;
7. вирусные эффекты.

ТИПОВЫЕ КОНФЛИКТЫ:

К-1. Высокий demand + высокая content saturation:
→ насыщенность НЕ является причиной отказа от темы.
  Аудитория большая, качественных экспертов мало (решение D-03).
→ тема берётся; данные 03 используются, чтобы выбрать
  собственный угол, глубину и подачу, а не чтобы запретить тему.
→ если угол пока не найден: всё равно можно CREATE,
  с пометкой в RISKS «угол близок к рынку».

К-2. Высокий viral signal + низкая expert value / client value:
→ DO NOT CREATE или TEST механизма на другой, ценной теме.
→ вирусная тема без экспертной ценности не берётся «ради охвата».

К-3. Сильная наука + отсутствие demand:
→ 06 свободен в выборе, жёсткого правила нет (решение D-03).
→ можно не брать и ориентироваться на спрос и реакции аудитории;
  можно опубликовать и смотреть на реакцию.
→ 05 при этом продолжает искать науку автономно:
  свобода касается только выбора темы в 06, а не научного поиска.

К-4. Высокий demand + мало громких исследований по теме:
→ создаём, но без формулировок «исследования доказали»,
  если таких исследований нет.
→ формат: различения и карты понимания, опираясь на научные
  факты, имеющиеся исследования и базу психологии.
→ FACT-CHECK REQUIRED, если звучит любой checkable claim.

К-5. У конкурентов залетело, у Татьяны такого ещё не было:
→ публикуем и смотрим на динамику (PUBLICATION MODE = TEST,
  с метрикой и датой проверки).
→ чужой результат не считается гарантией (04, раздел 33).

К-6. Собственный outlier без внешнего сигнала:
→ сильный кандидат на повтор механизма, но причина остаётся HYPOTHESIS.

К-7. Тема требует индивидуальной оценки (диагностика, клинический случай):
→ публичный формат только как объяснение механизма и границ.
→ при риске therapy conversion: DO NOT CREATE в этом формате.


--------------------------------------------------
3.4. ШАГ 4 — ВЕРДИКТ
--------------------------------------------------

Каждый кандидат получает один вердикт:

CREATE          — делаем в этом цикле
TEST            — делаем как тест (на GATE 1 предлагается APPROVE AS TEST)
NOT NOW         — откладываем, остаётся в BACKLOG
DO NOT CREATE   — не делаем, с причиной

TEST всегда содержит:
— гипотезу;
— метрику, по которой будем судить;
— через сколько дней снимаем метрику;
— что считаем подтверждением и опровержением.

DO NOT CREATE тоже является результатом 06 и попадает в отчёт
(раздел «чего мы не делаем»).


--------------------------------------------------
3.5. REQUIRED EVIDENCE INPUTS ПО ТИПУ РЕШЕНИЯ
--------------------------------------------------

Обязательные источники зависят от типа решения:

ТИП РЕШЕНИЯ                 | ОБЯЗАТЕЛЬНО          | ЕСЛИ НЕТ
DEMAND-LED                  | 02                   | HYPOTHESIS / TEST
SCIENCE-LED                 | 05                   | нельзя создавать научный claim
VIRAL MECHANISM TEST        | 04 (+ 01)            | TEST

POSITIONING / DIFFERENTIATION | 03                 | HYPOTHESIS / TEST
EXPERT-LED                  | экспертиза Татьяны   | допустимо, маркировка EXPERT JUDGEMENT

Остальные источники = AVAILABLE, но не обязательные.
Отсутствие необязательного источника не отменяет решение.

4. АУДИТОРИЯ
==================================================

Для каждого решения 06 фиксирует четыре поля (00, раздел 12):

WHO IS CONTENT ABOUT
WHO IS IT FOR
WHO IS EXPECTED TO ACT
RELATIONAL POSITION

Плюс AUDIENCE CONTOUR недели: WOMEN / MEN / COUPLES / GENERAL.

Проверка: «контент про мужчин» ≠ «контент для мужчин».
Аудитория системы (Татьяна, 08–09.10.2026): клиенты, не коллеги;
вся русскоязычная аудитория (Россия, Бишкек и дальше),
мужчины и женщины. Примеры без привязки к стране,
гео-хэштеги не ставим.

Гендерный режим текста (GENDER MODE) 06 назначает сам:
ДЛЯ МУЖЧИН: мужские примеры, действие через глаголы;
ДЛЯ ЖЕНЩИН: можно через эмоции и ощущения;
ОБЩИЙ: нейтрально, чтобы принял на свой счёт любой.

Не берём: true crime и шок-истории; препараты; гормоны
глубже связки с желанием; контент для психологов.

5. ФОРМАТ И МАРШРУТ
==================================================

--------------------------------------------------
5.1. ВЫБОР ФОРМАТА
--------------------------------------------------

Формат выбирается по функции, а не по привычке:

REEL       — discovery, recognition, быстрый reframe
CAROUSEL   — сохранение, различения, карта, объяснение механизма
POST       — более глубокая траектория в ленте
TELEGRAM   — та же тема, глубже: исследования, нюансы, кейсы
THREADS    — короткая выжимка темы дня, тезис, спор, reframe
STORIES    — подводка к теме дня + стикер (опрос, вопрос, слайдер)
VK         — по умолчанию версия Telegram + картинки

Одна тема ≠ одна неделя. Одна идея ≠ один asset.
Если из одного решения выходит несколько assets,
создаётся CONTENT FAMILY ID.


--------------------------------------------------
5.2. ВЫБОР PRODUCTION ROUTE
--------------------------------------------------

ROUTE A — всё, что не карусель (Reel, post, Telegram, Threads, Stories).

ROUTE B — карусель, если:
— у неё есть общий текстовый «корень» с другими assets семьи
  (например, Telegram-пост и карусель на одну мысль);
— или тема требует, чтобы сначала был написан и проверен
  полноценный текст.

Перед GATE 1 каждая строка плана сверяется с repeat/REGISTRY.md
по протоколу 10 (D-28): тема с углом за 8 недель, сцена/предмет/метафора
за 4 недели, кейсы за всё время; для кейса в плане указать вид
(с инструментом / рассказ) и скелет; пометки идут строкой «повтор: …».

Цепочка Route B (решение D-02):
06 → GATE 1 → 07 → HNE → 08 (если нужен) → 07 FINAL EDIT
→ 09 CAROUSEL BUILD → CAROUSEL QC → GATE 2 → READY_TO_PUBLISH.

ROUTE C — карусель, если:
— она самостоятельная и её смысл полностью описывается
  Carousel Brief от 06;
— отдельный длинный текст для неё не нужен.

Цепочка Route C:
06 → GATE 1 → 09 PRODUCTION (с HNE для текста слайдов)
→ 08 (если нужен) → 09 FINAL EDIT → CAROUSEL QC → GATE 2
→ READY_TO_PUBLISH.

Если сомневаешься между B и C: выбирать B.


--------------------------------------------------
5.3. FACT-CHECK REQUIREMENT
--------------------------------------------------

REQUIRED, если в asset планируется хотя бы один checkable claim:
научный, медицинский, статистический, причинный, диагностический,
про эффективность, про распространённость, про физиологию,
про классификации, психологический claim, поданный как факт.

Если 06 не уверен: REQUIRED.

NOT_REQUIRED только если asset заведомо состоит из
рефлексии, вопроса, наблюдения, личной позиции без
фактических утверждений.

07 и 09 могут повысить NOT_REQUIRED до REQUIRED (escalation).
Понизить не может никто.


--------------------------------------------------
5.4. SEPARATE VISUAL PRODUCTION (только Route A)
--------------------------------------------------

REQUIRED, если asset нуждается в изготовленном визуале:
AI-видео, AI-изображения, схемы, анимация, обложка-постер.

NOT_REQUIRED, если визуал не нужен или он входит в съёмку
(talking head, который Татьяна записывает сама).

Исполнитель VISUAL_PRODUCTION: 07 (визуальный блок 07,
разделы 18–28 и 45–47 протокола 07).

Для Route B и C: NOT_REQUIRED, визуал входит в 09.

8. ОБЪЁМ, НЕДЕЛЬНАЯ КАРТА И СЛОТЫ
==================================================

--------------------------------------------------
8.1. ОБЪЁМ
--------------------------------------------------

Норма Татьяны (09.10.2026, 00 раздел 57): пост каждый день.

06 определяет объём от:
— количества сильных CREATE и TEST решений;
— производственного ресурса недели (включая время Татьяны
  на запись, обложки и два гейта);
— требований разнообразия.

Обязательно в каждом цикле:
— минимум один Telegram output.

Модель недели (утверждена Татьяной 09.10.2026):
— 7 постов: 3 Reels, 3 карусели, 1 текстовый пост с фото;
— минимум 6 рубрик: Мужчины, Женщины, Отношения, Секс,
  Наука, Кейсы; каждая хотя бы раз;
— у каждой рубрики своя тема, не больше двух публикаций
  на одну тему (с недели 20–26.10);
— полезность недели: одна практическая карусель-инструмент,
  открыто, без кодовых слов; в Telegram и VK тот же
  инструмент файлом, если он есть;
— кейсы собирательные, по references/CASE_STRUCTURE.md,
  формат кейса (пост или кейс-Reel: картинки + отдельный текст
  озвучки, монтирует Татьяна, D-17) решается на GATE 1;
— наука по всему полю (отношения, конфликты, мужчины,
  женщины, сексология, пары), не только тема недели;
— к каждой теме комплект площадок и сторис (раздел 8.4).
